# Архітектурні рішення (ADR)

Важливі рішення щодо zoho-studio: що вирішили, чому і що з цього випливає. ADR потрібен, коли без
причини вибору рішення незрозуміле або його захочеться переглянути.

[English](../../en/adr/README.md)

## Коли писати

ADR пишуть для дорогих і важко зворотних рішень. Код показує, *як* усе працює, але не *чому* так
вирішили, а причини забуваються швидше за код.

Рішення варте ADR, якщо:

- його важко чи дорого відкотити: воно змінює контракт, формат даних чи файлів, розташування
  файлів, від яких залежать проєкти користувача, або спосіб встановлення;
- мало реальні альтернативи, і причину вибору варто пам'ятати;
- без нього незрозуміла поточна поведінка CLI.

Легко зворотному рішенню, деталі реалізації чи разовій домовленості ADR не потрібен: досить
повідомлення коміту. ADR — це ще й спосіб продумати рішення: якщо його не вдається чітко
сформулювати, рішення, можливо, ще не готове.

ADR додається тільки з погодження користувача.

## Формат

Файл `NNNN-<тема>.md`: четвірковий номер по порядку і тема в kebab-case
(`0001-single-repository-version.md`). Номери не перевикористовуються. Той самий файл є в
`docs/en/adr/`.

```markdown
# NNNN. <Рішення одним реченням>

- **Статус:** Прийнято | Замінено [NNNN](NNNN-<тема>.md) | Відхилено
- **Дата:** YYYY-MM-DD

## Рішення

<Що вирішено — коротко, на початку.>

## Контекст

<Обмеження й обставини: вимоги, сумісність, вартість, допустима ціна помилки.>

## Альтернативи

<Що розглядали і чому відкинули. Можна пропустити, якщо альтернатив не було.>

## Наслідки

<Що з цього випливає: що стає простіше, що складніше, які правила з'являються.>

## Межі

<Коли рішення доречне і що зробить його неактуальним — сигнал переглянути.>
```

Прийнятий ADR не переписують: він фіксує, що і чому вирішили тоді. Коли рішення переглядають,
пишуть новий ADR, а в старому змінюють тільки статус.
