# Міграції

Міграція — це файл TypeScript у `migrations/zoho-crm/`, що описує новий модуль Zoho CRM з
його полями або поля, які треба додати до вже наявного модуля. `bun run migrate` у проєкті
перевіряє її щодо організації, до якої виконано вхід у проєкті, і після вашого підтвердження створює
те, що в ній описано.

**Міграція лише створює.** Вона ніколи не змінює й не видаляє поле, і нічого зі створеного нею не можна
скасувати через неї: у Zoho немає API, що видаляє модуль. Спершу випробуйте міграцію на sandbox.

```bash
bun run migrate                         # pick a migration from the list
bun run migrate 001-projects --dry-run  # show the plan and the conflicts, change nothing
bun run migrate 001-projects --yes      # run without the confirmation prompt
```

Скрипт постачається з проєктом, створеним [`zoho-studio init`](3-init-command.md), і потребує
підключених пакетів (`bun install` після `bun run link`, див. [init](3-init-command.md#скрипти)) та
[входу](4-login-command.md).

## Файл міграції

Ім'я файлу без `.ts` — це назва міграції, а список показує міграції в порядку назв,
тож префікс зберігає їх у тому порядку, в якому їх написано: номер, доповнений нулями
(`001-projects`), або дата й час, які ставить [`z-crm:migrations:make`](32-migrations-make-command.md). Файл оголошує рівно одну дію.

```ts
import { defineMigration } from '@zoho-studio/zoho-crm/migrations'

export default defineMigration({
    create: {
        api_name: 'Projects',
        singular_label: 'Project',
        plural_label: 'Projects',
        profiles: ['Administrator', 'Standard'],
        fields: (schema) => {
            schema.text('Code', { api_name: 'Code', length: 50 })
            schema.currency('Budget', { decimal_place: 2 })
            schema.picklist('Stage', { values: ['New', 'Active', 'Done'] })
            schema.lookup('Account', { module: 'Accounts' })
        },
    },
})
```

`create` створює новий модуль. `api_name` необов'язковий — тоді Zoho виводить його з `plural_label`, — а
`profiles` називає профілі, які отримують модуль; якщо його пропустити — лише `Administrator`. Назви
профілів — ті, що зберігає [`z-crm:profiles:pull`](26-profiles-pull-command.md).

`update` додає поля до наявного модуля:

```ts
export default defineMigration({
    update: {
        module: 'Projects',
        fields: (schema) => {
            schema.boolean('Archived')
        },
    },
})
```

У новому проєкті є приклад для копіювання в `scripts/example-migration.ts.txt`, а
[`zoho-studio z-crm:migrations:make`](32-migrations-make-command.md) створює файл, названий за
датою й часом, із заповненою дією.

## Типи полів

Кожен метод приймає мітку поля (до 25 символів) та опції. Дві опції приймають
усі методи:

- `api_name` — якщо його пропустити, Zoho виводить його з мітки;
- `tooltip` — підказка для того, хто заповнює поле. Сам текст, до 255 символів, показується як
  іконка інформації поруч із полем, і `{ type: 'info_icon', text }` — те саме.
  `{ type: 'static_text', text }`, до 35 символів, натомість показує підказку всередині порожнього поля;
  Zoho приймає її лише для полів, у які вводять текст, — text, email, phone, website, integer,
  bigint, double, percent, currency і lookup.

Решта опцій зберігають назви Zoho, а пропущена опція отримує значення Zoho за замовчуванням.

| Метод | Опції |
|---|---|
| `text`, `phone` | `length` |
| `textarea` | `size`: `small` (за замовчуванням), `large` або `rich_text` |
| `email`, `website`, `date`, `datetime`, `boolean`, `userlookup` | — |
| `integer`, `bigint` | `length` |
| `double` | `length`, `decimal_place` |
| `percent` | `decimal_place` |
| `currency` | `length`, `decimal_place`, `rounding_option`, `precision` |
| `picklist`, `multiselectpicklist` | `values`: рядки або пари `{ display_value, actual_value }` |
| `lookup` | `module` (обов'язкова), `display_label` — мітка пов'язаного списку, за замовчуванням мітка поля |

## Що перевіряється перед запуском

Будь-що з цього блокує запуск, і скрипт виводить кожен пункт:

- файл не завантажується, називає опцію, якої тип поля не має (скажімо, `decimal_places` з
  помилкою), задає опції значення неправильного виду (`length: '50'`) або порушує
  правило, яке Zoho відхилив би: довжину міток, формат API-імені,
  мітку чи API-ім'я, оголошені двічі, порожнє чи повторене значення списку вибору, задовгу підказку або
  підказку типу, який поле не підтримує;
- для `create` — модуль з тим самим API-ім'ям чи міткою вже існує або поле збігається з
  полями, які Zoho додає до кожного нового модуля (`Name`, `Owner`, `Email`, `Secondary_Email`, `Tag`, …);
- для `update` — модуль не існує або поле з тією самою міткою чи API-ім'ям уже
  є в ньому — назви порівнюються без урахування регістру;
- lookup вказує на модуль, якого не існує, зокрема на модуль, який створює ця сама
  міграція;
- назва профілю невідома;
- міграцію вже застосовано до цієї організації (див. журнал нижче).

## Запуск

Перед планом скрипт називає організацію, до якої йде міграція, з її типом великими
літерами — зеленим для sandbox, червоним для всього іншого:

```text
Organization: Acme (7000000012345) — SANDBOX
```

Запитання-підтвердження теж її називає, а все, що не sandbox, називає `PRODUCTION`. З
`--yes` запитання немає, але рядок усе одно виводиться.

Спершу створюється модуль, потім поля, до 25 за запит. Запуск зупиняється на першому
кроці, який Zoho відхиляє; для полів скрипт виводить, які з них не вдалося створити й чому. Після запуску — і невдалого
теж, якщо модуль уже існує, — модуль зчитується назад із Zoho, скрипт повідомляє, які заплановані
поля існують, а яких бракує, і папка модуля в `data/zoho-crm/modules/` оновлюється —
якщо це зчитування не вдається, скрипт про це каже, і запуск усе одно записується в журнал, — так, як записали б її [`z-crm:modules:pull`](7-modules-pull-command.md) і
[`z-crm:fields:pull`](8-fields-pull-command.md).

Код виходу — 0, коли міграцію застосовано, пробний запуск не знайшов конфліктів або ви відхилили
запит, і 1 в інших випадках.

## Журнал

Кожен запуск записується в `.zoho-studio/migrations.json`, окремо для кожної організації, тож
проєкт, що вказує спершу на sandbox, а потім на production, зберігає обидві історії. Застосовану міграцію
не можна запустити знову на тій самій організації; список показує її як застосовану. Невдалу
позначено як невдалу, і її можна запустити знову, але все, що вона вже створила, тепер вважається конфліктом —
завершіть роботу новою міграцією `update`.

Журнал зберігається на вашому комп'ютері: `init` не пускає його в git, а запусків колеги в ньому немає.
У проєкт, створений до появи міграцій, треба вручну додати `migrations.json` до
`.zoho-studio/.gitignore`.

## Дозволи

Для створення потрібні `ZohoCRM.settings.modules.CREATE` і `ZohoCRM.settings.fields.CREATE`, а
перевірки читають модулі, поля й профілі. Усі вони є в
[налаштуваннях](2-settings.md) за замовчуванням, і `ZohoCRM.settings.ALL` теж їх охоплює.

## Вивід для інших програм

`--json` виводить по одному об'єкту JSON на рядок замість читабельного звіту: спершу
`{ "type": "prepared", "migration": …, "organization": { "id", "company_name", "type" } }` з
планом, конфліктами й цільовою організацією, потім по одній події на кожен
крок, на результат кожного поля, на перевірку і фінальний `finished` з `applied`, `failed` або
`blocked`. Міграція з конфліктами завершується одразу після `prepared` з `finished` зі значенням `blocked`; пробний
запуск без конфліктів завершується на `prepared`. Вона ніколи не ставить запитань, тож потребує назви міграції та
`--yes` або `--dry-run`.
