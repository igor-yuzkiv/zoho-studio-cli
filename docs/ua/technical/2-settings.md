# Налаштування

Проєкт зберігає все потрібне в **одному файлі**: `.zoho-studio/settings.json`. Його читає кожна
команда, а створює [`zoho-studio init`](3-init-command.md).

**Файл не містить секретів.** Секрети клієнтів і токени зберігаються поза проєктом, у
`~/.zoho-studio` — див. [`zoho-studio login`](4-login-command.md). Проте `init` кладе поруч із
файлом `.gitignore`, який не пускає його й `org.json` у git, і записує файл із `chmod 0600`.

## Файл

```json
{
    "auth": {
        "baseUrl": "https://accounts.zoho.com",
        "scopes": [
            "ZohoCRM.settings.modules.READ",
            "ZohoCRM.settings.fields.READ",
            "ZohoCRM.settings.workflow_rules.READ",
            "ZohoCRM.settings.functions.READ",
            "ZohoCRM.org.READ",
            "ZohoCRM.settings.client_scripts.READ",
            "ZohoCRM.settings.static_resources.READ",
            "…"
        ]
    },
    "api": {
        "baseUrl": "https://www.zohoapis.com",
        "version": "v8"
    },
    "logs": {
        "file": "logs/zoho-studio-cli.log"
    },
    "presets": {
        "pull-crm": ["z-crm:org:info", "z-crm:modules:pull", "…"]
    }
}
```

**Куди потрапляють завантажені файли, не налаштовується.** Кожен артефакт лягає в `src/` за
фіксованим шляхом — `src/zoho-crm/functions`, `src/zoho-crm/modules`, `src/zoho-crm/workflows`, — щоб CLI міг покладатися на цю структуру.
Усе дерево див. у [`zoho-studio init`](3-init-command.md).

Кожне значення у файлі — **ваше**: ви його заповнюєте, CLI лише читає.

`auth.baseUrl` і `api.baseUrl` визначають дата-центр Zoho. Типово це дата-центр США; для облікового
запису в іншому регіоні обидва значення треба змінити на домен цього регіону — для Європи
`https://accounts.zoho.eu` і `https://www.zohoapis.eu`; так само `.in`, `.com.au`, `.jp`, `.ca`, `.com.cn`.

`logs.file` — куди кожна команда пише свій лог, відносно кореня проєкту; його папка створюється з
першим записаним рядком. Типове значення — `logs/zoho-studio-cli.log`, а папка `logs/`, яку
створює `init`, містить `.gitignore`, що не пускає `*.log` у git. Якщо вказати інше місце, це вже
не діє — додайте новий шлях до свого `.gitignore` самі.

`auth.scopes` — список дозволів, які [`zoho-studio login`](4-login-command.md) запитує в Zoho; той
самий список з'являється на екрані згоди. Скоротіть його до того, чим справді користуєтеся: дозвіл,
якого CLI ніколи не отримав, він не зможе непомітно використати. Zoho фіксує дозволи в момент
згоди, тож проєкт, авторизований до того, як додали дозволи для клієнтських скриптів і статичних
ресурсів, має знову виконати `login`, перш ніж запрацюють їхні команди `z-crm:*:pull`.

`presets` дає назви послідовностям команд для [`zoho-studio preset`](24-preset-command.md). Як і
будь-який інший розділ, він зливається з вбудованим за ключами, тож доданий вами пресет стає поруч
із `pull-crm`, а не замінює його.

Кожен ключ необов'язковий. Усе, що ви пропустили, береться з вбудованих типових значень, тож
порожній об'єкт — це коректний проєкт. Ключ, який ви записали, **замінює** типове значення, а
не доповнює його — це стосується й списків, тож скорочений `auth.scopes`
лишається рівно таким коротким, яким ви його записали. Це також означає, що можна видалити ключ, щоб
повернутися до типового значення, замість того щоб шукати початкове.

Ключ, якого CLI не знає, зберігається й ігнорується.

## Як відбувається читання

`loadProjectSettings()` читає файл через [bunfig](https://github.com/stacksjs/bunfig) і глибоко
зливає його з типовими значеннями. `getProjectSettings()` обгортає її кешем, і саме її викликають
команди: вона піднімається від поточної папки до найближчого кореня проєкту й повертає і цей шлях,
і налаштування, тож команда працює з будь-якої підпапки й жодній команді не треба шукати проєкт
самій.

Три особливості, які варто знати, перш ніж на них покладатися:

- **Поза проєктом вона завершується помилкою.** `getProjectSettings()` кидає помилку з підказкою
  запустити `init`, коли жодна батьківська папка не містить файлу налаштувань. Лише низькорівнева
  `loadProjectSettings()` мовчки повертає типові значення для відсутнього файлу.
- **Змінні середовища ігноруються.** Інакше bunfig зіставляв би префікс `SETTINGS_*` із типовими
  значеннями, і випадковий `SETTINGS_API_BASEURL` у вашій оболонці непомітно замінив би значення,
  про яке файл проєкту навіть не згадує. Це вимкнено.
- **Прочитане кешується на весь час роботи процесу.** Один запуск читає налаштування з кількох
  місць і має бачити одну узгоджену картину, тож зміни, внесені ззовні під час роботи команди, не
  підхоплюються.

## Як відбувається запис

bunfig лише читає, тож `saveProjectSettings()` записує файл сама: серіалізує весь об'єкт у JSON,
за потреби створює папку, застосовує `chmod 0600` і оновлює кеш, щоб решта запуску бачила нові
значення.

Вона завжди записує **весь** об'єкт. Щоб змінити одне значення, прочитайте налаштування, змініть
поле й запишіть результат назад — не передавайте їй частковий об'єкт.

## Де лежить код

| Файл | Роль |
| --- | --- |
| `src/config.ts` | Назви файлів і папок, спільні для всіх областей, і допоміжні функції для шляхів |
| `src/zoho-crm/zoho-crm.config.ts` | Фіксовані назви папок артефактів CRM |
| `src/settings/types.ts` | Форма `ProjectSettings` |
| `src/settings/default.settings.ts` | Типові значення, з якими зливається кожне читання |
| `src/settings/settings.loader.ts` | `loadProjectSettings()`, `findProjectPath()` |
| `src/settings/settings.store.ts` | `getProjectSettings()`, `saveProjectSettings()`, кеш |

`saveProjectSettings()` отримує шлях до проєкту явно — `init` записує найперший файл налаштувань,
коли ще немає проєкту, який можна було б знайти.
