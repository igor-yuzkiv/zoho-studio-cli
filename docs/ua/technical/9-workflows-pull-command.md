# `zoho-studio z-crm:workflows:pull`

Завантажує кожне правило робочих процесів Zoho CRM у пласку папку `src/zoho-crm/workflows/` — по одному JSON-файлу на правило,
разом з умовами та діями, яких немає в самому списку правил.

```bash
zoho-studio z-crm:workflows:pull
```

```text
Pulling workflow rules |████████████████████| 77/77 | Send Welcome Email
Workflow rules found: 77
Workflow rules saved: 77
Workflow rules failed: 0
```

Команда потребує проєкту, який пройшов [`zoho-studio login`](4-login-command.md), з наданим
дозволом `ZohoCRM.settings.workflow_rules.READ`. Вона не залежить від жодної іншої команди
завантаження: правила надходять з API і записуються у власну папку, тож
[`z-crm:modules:pull`](7-modules-pull-command.md) ні не постачає їй даних, ні не перезаписує її.

Правила отримуються по одному — запит списку, а потім по одному запиту на кожне правило за його повним записом, —
з короткою затримкою між ними, щоб не впертися в ліміти API Zoho. Організація зі сотнею
правил обробляється приблизно хвилину. Індикатор прогресу показує правило, яке завантажується зараз.

## Що з'являється на диску

```text
src/zoho-crm/workflows/
├── Big Deal Rule.json
├── Contacts.Server.Upsert.json
└── Send Welcome Email.json
```

Кожен файл містить повний запис правила таким, яким його повернув `GET /settings/automation/workflow_rules/{id}`,
відформатований з відступом у чотири пробіли й завершальним переведенням рядка. Цей запис містить `conditions` —
критерії, миттєві дії та заплановані дії, — і саме це робить знімок вартим
читання. Самі дії подано як посилання (назва, id, тип); їхній вміст доступний через
окремі ендпоінти й не завантажується.

Папка завжди `src/zoho-crm/workflows/`; жодне налаштування її не переносить.

**Уся папка видаляється й створюється заново під час кожного повного запуску**, тож правило, видалене в Zoho, зникає
й локально, а будь-яка локальна правка втрачається.

Файли названо за правилом. Замінюються лише символи, яких не може бути в сегменті шляху; більше нічого
в назві не змінюється. Назви правил не унікальні, тож коли два правила претендують на одне й те саме
ім'я файлу, друге отримує ще й свій id — `Move Files.1000000000000012345.json`. Правила
обробляються у фіксованому порядку, тож повний запуск завжди називає їх однаково. Яке з двох дублікатів
отримає просту назву, все ж може змінитися, якщо папку було зібрано запусками з `--module`, а потім перезібрано
повним запуском — обидва правила зберігаються в будь-якому разі, але пара виглядатиме як перейменування.

## Один модуль за раз

`--module` звужує запуск до правил одного модуля:

```bash
zoho-studio z-crm:workflows:pull --module=Deals
```

Такий запуск **не** стирає папку. Він видаляє лише файли, правило яких належить цьому модулю, —
кожен файл записує власний модуль, тож власника зчитують із самого файлу, — і лишає кожне інше
правило на місці. Файл, який не вдається прочитати як правило, лишається недоторканим, а не вгадується.

Значення — API-назва модуля. Значення, яке не є простою назвою, відхиляється ще до того, як щось буде
видалено, а модуль, якого Zoho не знає, зупиняє команду з власним повідомленням Zoho.

## Збої

Правило, повний запис якого не вдається отримати, не зупиняє запуск: воно потрапляє в підсумок
із коротким описом помилки, решта правил усе одно завантажується, і команда все одно завершується успішно.

```text
Workflow rules failed: 1
  - Big Deal Rule: The value provided to the param is Invalid (INVALID_MODULE)
```

Неможливість отримати *список* правил фатальна — записувати нічого.

## Логи

CLI пише структуровані JSON-логи в [`logs.file`](2-settings.md), типово `logs/zoho-studio-cli.log`.
`z-crm:workflows:pull` фіксує початок запуску, скільки правил знайдено, підсумкові кількості
та кожен збій зі стеком викликів. Окремі успішні правила не потрапляють у лог — їх уже показує
індикатор прогресу.
