# `zoho-studio z-crm:workflow-actions:pull`

Завантажує кожну дію робочих процесів Zoho CRM у `src/zoho-crm/workflow-actions/` — по одному JSON-файлу на дію,
згруповано за типом дії, разом з конфігурацією, якої немає в самому списку дій.

```bash
zoho-studio z-crm:workflow-actions:pull
```

```text
Pulling workflow actions |████████████████████| 92/92 | webhooks: Contacts.Server.Upsert
Workflow actions found: 92
Workflow actions saved: 92
Saved from the list, because Zoho returned no details: 0
Failures: 0
```

Команда потребує проєкту, який пройшов [`zoho-studio login`](4-login-command.md), з наданим
дозволом `ZohoCRM.settings.automation_actions.READ`. Проєкти, створені до появи цього дозволу,
мають додати його в `auth.scopes` у [`.zoho-studio/settings.json`](2-settings.md) і увійти
знову; команда про це повідомляє, коли Zoho відхиляє запит.

Вона не залежить від жодної іншої команди завантаження. [`z-crm:workflows:pull`](9-workflows-pull-command.md)
завантажує правила, які *використовують* ці дії, і обидві команди пишуть в окремі папки — правило посилається
на свої дії за назвою та id, а ця команда наповнює ці посилання вмістом.

Дії отримуються по одній — запит списку для кожного типу, а потім по одному запиту на кожну дію за її
повним записом, — з короткою затримкою між ними, щоб не впертися в ліміти API Zoho. Організація
зі сотнею дій обробляється приблизно хвилину. Індикатор прогресу показує дію, яка завантажується
зараз, з її типом на початку.

## Що з'являється на диску

```text
src/zoho-crm/workflow-actions/
├── email-notifications/
│   └── Send Welcome Email.json
├── field-updates/
│   └── Set Lead Status.json
├── functions/
│   └── wf_leads_assignOwner.json
├── tasks/
│   └── Follow Up Call.json
└── webhooks/
    └── Contacts.Server.Upsert.json
```

Є п'ять типів дій, і кожен має власну папку:

| Папка | Як його називає Zoho | Що повний запис додає до списку |
|---|---|---|
| `email-notifications` | `email_notifications` | `recipients`, `bulk_email` |
| `field-updates` | `field_updates` | нічого — список уже повний |
| `tasks` | `tasks` | нічого — список уже повний |
| `webhooks` | `webhooks` | `body`, `headers`, `authentication`, `url_parameters`, `date_time_format` |
| `functions` | `functions` | `arguments` |

Кожен файл містить повний запис дії таким, яким його повернув `GET /settings/automation/{type}/{id}`,
відформатований з відступом у чотири пробіли й завершальним переведенням рядка. Для невеликої
кількості дій, які Zoho загалом нормально показує в списку, він не повертає подробиць; такі файли містять натомість запис зі списку, і запуск
повідомляє, які саме:

```text
Saved from the list, because Zoho returned no details: 1
  - field_updates: Set Lead Status
```

Для оновлення поля чи завдання це нічого не втрачає: там запис зі списку вже є повним записом.
Для інших трьох типів файл — неповний запис, тому про нього повідомляється, а не
пропускається мовчки.

Дія `functions` записує, яку функцію вона викликає і з якими аргументами; сам код Deluge
надходить із [`z-crm:functions:pull`](6-functions-pull-command.md).

Папка завжди `src/zoho-crm/workflow-actions/`; жодне налаштування її не переносить.

**Папка типу видаляється й створюється заново під час кожного повного запуску**, тож дія, видалена в Zoho,
зникає й локально, а будь-яка локальна правка втрачається. Тип, запит списку якого не вдався, зберігає попередній
вміст недоторканим.

Файли названо за дією. Замінюються лише символи, яких не може бути в сегменті шляху;
більше нічого в назві не змінюється. Назви дій унікальні в межах модуля, але не в межах
організації, тож коли дві дії одного типу претендують на одне й те саме ім'я файлу, друга
отримує ще й свій id — `Send Reminder.1000000000000012345.json`. Дії обробляються у
фіксованому порядку, тож повний запуск завжди називає їх однаково.

## Звуження запуску

`--type` завантажує один тип дій і приймає або назву папки, або назву, яку використовує Zoho:

```bash
zoho-studio z-crm:workflow-actions:pull --type=webhooks
zoho-studio z-crm:workflow-actions:pull --type=email-notifications
```

Перезаписується лише папка цього типу; інші чотири лишаються недоторканими.

`--module` звужує запуск до дій одного модуля:

```bash
zoho-studio z-crm:workflow-actions:pull --module=Deals
```

Такий запуск **не** стирає жодної папки. У папці кожного типу він видаляє лише файли, дія яких
належить цьому модулю, — кожен файл записує власний модуль, тож власника зчитують із самого
файлу, — і лишає кожну іншу дію на місці. Файл, який не вдається прочитати як дію, лишається
недоторканим, а не вгадується.

Обидві опції поєднуються, і кожну перевіряють ще до того, як щось буде видалено: `--module` приймає
API-назву модуля, `--type` — один із п'яти типів вище.

```bash
zoho-studio z-crm:workflow-actions:pull --module=Deals --type=webhooks
```

## Збої

Тут ніщо не фатальне, бо кожен тип незалежний.

Дія, повний запис якої не вдається отримати, — відхилений запит, а не порожня відповідь, описана вище, —
потрапляє в підсумок із коротким описом помилки, а решта дій усе одно завантажується. Про тип, *список* якого
не вдається отримати, повідомляється так само, його папка лишається як була, а інші типи
все одно обробляються.

```text
Failures: 1
  - tasks: permission denied (OAUTH_SCOPE_MISMATCH) — add "ZohoCRM.settings.automation_actions.READ" to auth.scopes in .zoho-studio/settings.json and run "zoho-studio login" again.
```

## Логи

CLI пише структуровані JSON-логи в [`logs.file`](2-settings.md), типово `logs/zoho-studio-cli.log`.
`z-crm:workflow-actions:pull` фіксує початок запуску, скільки дій знайдено і в скількох
типах, підсумкові кількості та кожен збій зі стеком викликів. Окремі успішні
дії не потрапляють у лог — їх уже показує індикатор прогресу.
